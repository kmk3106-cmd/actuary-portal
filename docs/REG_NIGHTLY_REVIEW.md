# 규정 개정이력 야간 점검 (매일 00:00 KST, 2시간)

매일 00:00 KST 에 Claude 예약 세션("규정이력 야간 점검")이 켜져서 규정 개정이력의 **① 같은 주제 묶음 번호** 와 **② 계리결산팀 관련성** 을
사람 눈으로 보듯 검토해 설정 파일을 고치고 포탈에 반영한 뒤 커밋한다. **02:00 KST 가 되면 하던 일을 멈춘다** (팀장 지시: 토큰은 하루 2시간치만).

## 1. 구성

| 항목 | 내용 |
|---|---|
| 스케줄 | Claude 예약 작업 "규정이력 야간 점검", 매일 **00:00 KST** 새 세션. 02:52 의 "일일 포탈 자체점검" 과 겹치지 않도록 02:00 전 종료 |
| 묶음 SSOT | `config/reg_topic_groups.json` — groups[{no, label, event_ids[], note}] |
| 관련성 SSOT | `config/reg_relevance.json` — overrides{event_id: {relevance, reason}} + keywords |
| 적용 스크립트 | `scripts/apply_reg_review.py --base-url https://portal.kkuks.com --groups --relevance` (PATCH 뒤 재조회로 확인) |
| 화면 | `reg-history.html` 타임라인: 확정 묶음은 체크 아이콘 칩 "묶음 N", 파일에 없는 건만 제목 핵심어로 자동 추정(링크 아이콘). 관련성 필터 기본값 "관련 + 참고" |
| 재적재 | `scripts/load_reg_history.py` 가 묶음 파일을 읽어 `topic_group_*` 를 함께 쓰므로 06:00 동기화·재적재에도 유지 |
| 로그 | `docs/qa/REG_REVIEW_LOG.md` 에 한 줄씩 누적 |

## 2. 시간 규칙 (KST)

- **00:00 시작, 02:00 종료.** 01:45 가 지나면 새 판단에 들어가지 않고, 끝난 것만 적용·커밋한다. 못 끝낸 것은 로그에 "다음 날" 로 남긴다.
- 이 시간대엔 푸시 금지 구간(05:45~06:45)이 아니므로 바로 푸시한다. 정적 파일·config 만 바뀌므로 node 재시작은 없다.
- 02:52 자체점검(`docs/QA_DAILY_CHECK.md`)과 파일이 겹치지 않는다. 겹칠 일이 생기면 야간 점검이 먼저 끝난 상태여야 한다.

## 3. 점검 내용

### 3-1. 같은 주제 묶음 (reg_topic_groups.json)
- **매일 새로운 시각으로 전체를 다시 본다 (팀장 지시 2026-10-19).** 전날 확정한 묶음·번호·관련성은 참고일 뿐 정답이 아니다. 기존 묶음도 원문(제목·요약·조문·부칙·보도자료 본문)을 근거로 다시 판단해 틀렸으면 고치고, 고친 이유를 note 와 로그에 한 줄 적는다. 전날과 같다는 이유로 그대로 두지 않고, 바꿀 근거가 없을 때만 유지한다.
- 포탈에서 `GET /tables/reg_items?limit=5000` 으로 전체를 받아 **제목·한 줄 요약·규정명·조문·날짜·상태** 를 읽고, 필요하면 kb 리포트 본문(`report_doc_id`)까지 본다.
- **같은 묶음의 기준**: 하나의 개정 사안이 예고 → 발령 → 시행으로 이어지는 흐름과, 그 사안을 설명하는 보도자료. 규정이 달라도(감독규정 예고 → 시행세칙 예고 → 보도자료) 같은 사안이면 한 묶음.
  - 예: 2026-09-11 감독규정 규정변경예고(계리가정 내부통제·보고서) + 2026-09-11 보도자료(계리가정 관리 강화) + 2026-10-12 시행세칙 사전예고(계리가정 보고서 세부기준) = 한 묶음.
  - 예: 2026-04-08 세칙 예고(계리적 가정 경험통계기간) + 2026-06-29 보도자료(계리감독 선진화) + 2026-06-30 세칙 시행 = 한 묶음. 2026-06-19 예고(별표22·35 해약률)는 다른 사안.
  - 분기마다 반복되는 "업무보고서 서식 개정" 은 서식 묶음이 아니라 **각 분기 건을 따로** 둔다(이어지는 사안이 아니다).
  - 한 건만 있는 사안은 묶음에 넣지 않는다 (화면도 색을 안 칠한다).
- **번호**: 묶음 안 가장 오래된 날짜 순으로 1부터. 새 묶음이 생기거나 합쳐지면 **전체를 다시 매긴다** (번호 보존 안 함, 화면 칩은 번호만 보여 준다).
- **label**: 10~20자 사안 이름 (예: "계리가정 보고서 도입", "경험통계기간 적용기준"). `note` 에 판단 근거 한 줄.
- 화면이 자동 추정한 묶음과 다르게 판단했으면 그 이유를 로그에 쓴다. 자동 추정이 틀리는 패턴이 보이면 `reg-history.html` 의 `TOPIC_STOP`/`TOPIC_DAYS` 를 고치는 대신 **이 파일에 확정**하는 것을 우선한다 (화면 로직 수정은 팀장 승인 뒤).

### 3-2. 관련성 (reg_relevance.json overrides)
- 팀 업무는 **계리 · 상품 · 리스크** 다. 그 밖(영업·모집·판매채널·대리점·손해사정·자격시험·대출·일반 공시·회계기준원 행사 등)은 `무관` 으로 내려 화면 기본 필터("관련 + 참고")에서 빠지게 한다.
  - `관련`: IFRS17 부채결산·계리적 가정·경제적 가정·계리모델·선임계리사·해약환급금준비금·계약자배당 등 결산 수치에 직접 영향.
  - `참고`: 상품(상품구조·표준약관·사업방법서·상품위원회·실손 상품) · 리스크(K-ICS·지급여력·요구자본·ORSA·내부모형·위기상황분석·건전성).
  - `무관`: 나머지.
- 새로 수집된 건(overrides 에 없는 것)은 모두 판단해 overrides 에 넣는다. reason 은 "무엇이 왜" 한 줄.
- 화면에서 담당자가 확정한 건(`relevance_manual: true`)은 **절대 바꾸지 않는다**. overrides 와 다르면 로그에 "담당자 확정과 다름" 으로만 남긴다.

## 4. 절차 (세션이 그대로 따른다)

1. `git pull origin master` 뒤 이 문서와 두 설정 파일을 읽는다.
2. `python3 scripts/apply_reg_review.py --base-url https://portal.kkuks.com --groups --relevance --dry-run` 으로 현재 상태와 설정의 차이를 본다.
3. 포탈 데이터를 받아 §3 기준으로 판단하고 설정 파일 두 개를 고친다 (`updated_at`·`updated_by` 갱신).
4. `--dry-run` 으로 바뀔 건을 확인한 뒤 실제 적용: `python3 scripts/apply_reg_review.py --base-url https://portal.kkuks.com --groups --relevance --author-name 야간점검`. 스크립트가 재조회로 영속을 확인한다.
5. 브라우저 확인(가능하면): 샌드박스가 아니라 **실서버 화면을 읽기 전용으로** 열어 묶음 칩·필터가 맞는지 본다. 계정이 없으면 API 재조회 결과로 갈음하고 로그에 "화면 미확인" 으로 적는다.
6. `docs/qa/REG_REVIEW_LOG.md` 에 한 줄 추가 → 커밋 → `git push origin master` (+ `claude/great-shaw-4acfad-31ua6t` 미러). 커밋 메시지에 모델명·세션 외 식별자 금지.
7. 02:00 KST 가 되면 4~6 까지 끝난 범위만 남기고 종료.
