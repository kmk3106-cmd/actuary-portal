## 0. 한 줄 결론

지시서의 지적은 대부분 실제 데이터로 확인됐다. 가장 심한 것은 세 가지다.
1. **오연결** — 확정↔예고 자동 연결 25건 중 14건이 조문 겹침 없이 "같은 규정의 가장 가까운 예고" 로 추정한 것인데 화면에는 확정 연결처럼 보인다. 지시서가 든 `6/19 별표22·35 ↔ 6/29 ORSA 별표37` 건이 정확히 이 경우다.
2. **예정 시행일의 확정 표시** — 예고 53건 중 19건은 예고안 본문에서 긁은 "YYYY.MM.DD부터 시행" 이 진행 현황에 `시행 2027.01.01 (D-75)` 로 확정 색상으로 뜬다.
3. **제목이 변경 내용을 말하지 않음** — 예고·확정 92건 제목이 거의 "규정명 개정 — 공고문 취지 첫 문장 70자" 이고, 보도자료 44건은 홍보 헤드라인 그대로다.

이것들은 기존 데이터·화면·리포트를 지우지 않고 **필드 추가 + 라벨·판정 규칙 교체**로 고칠 수 있다. 아래 §2 가 그 최소 설계다.

## 2. P0 설계 — 최소 변경 (기존 데이터·화면·리포트·조치 보존)

### P0-1. 상태 사전 통일 (모든 화면이 같은 함수 하나로 문구를 낸다)

| stage 값 | 화면 문구 | 전이 조건 (근거 문서가 있어야 올라간다) |
|---|---|---|
| `notice_open` | 예고 중 · 미확정 | 예고문 있음, 의견마감 ≥ 오늘 |
| `notice_closed` | 의견수렴 종료 · 발령 미확인 | 예고문 있음, 의견마감 < 오늘, 발령문 없음 |
| `issued` | 발령 확인 · 시행 전 | 발령문(고시·확정 개정 게시) 있음, 시행일 미확인 또는 > 오늘 |
| `effective` | 시행 중 | 발령문 있음 **그리고** 시행일 `confirmed` ≤ 오늘 |
| `unknown` | 현재 단계 확인 필요 | 보도자료만 있음 / 원문 없음 |
| `withdrawn` | 철회 | 철회 문서 |

- 기존 `status`(사전예고·입법예고·공포·시행·보도자료·철회)는 **자료 유형**으로 그대로 두고 배지 문구만 바꾼다: `시행` → `확정 개정(발령)`, `공포` → `확정 고시(발령)`. 상태값은 바꾸지 않으므로 기존 데이터·필터·동기화가 그대로 돈다.
- `시행세칙`(규정 유형 배지)과 `시행 중`(단계)이 같은 줄에 안 오도록 단계는 제목 위 첫 줄, 규정 유형은 메타 줄에 둔다.

### P0-2. 날짜마다 확인 수준을 붙인다

`reg_items.date_status = { notice: 'confirmed'|'planned'|'unknown', comment_due:…, issuance:…, effective:…, first_closing:… }`

| 날짜 | 확정(confirmed) 조건 | 예정(planned) | 미확인 |
|---|---|---|---|
| 예고일 | 공고 게시물 날짜 | — | — |
| 의견마감일 | 공고문 필드 | — | 필드 없음 |
| 발령일 | 고시 게시물 날짜 · 금감원 제·개정 정보 게시일(**'게시일 기준' 표기**) | — | 발령문 없음 |
| 시행일 | 발령문 부칙 또는 발령 공고문에서 추출 + 원문 링크 | 예고안 본문 추출 → `시행 예정 YYYY.MM (예고안 기준)` | 둘 다 없음 |
| 최초 결산 반영일 | 담당자 입력 | 담당자 입력 | 기본값 |

- 화면: `예고 2026.06.19` · `의견마감 2026.07.29` · `발령 미확인` · `시행 예정 2026.10 (예고안 기준, 확정 아님)`. 미확인 칸에 날짜를 채우지 않는다.
- 진행 현황의 시행 스텝은 `confirmed` 만 초록, `planned` 는 점선·회색 "예정", `unknown` 은 "미확인".
- 적재 스크립트: 예고 건에서 추출한 시행일은 `date_effective` 에 넣지 않고 `date_effective_planned` 에 넣는다 (기존 19건은 마이그레이션으로 옮긴다).

### P0-3. 연결은 근거와 신뢰도를 기록하고, 약한 연결은 후보로만

`reg_items.relationships = [{ related_event_id, type: 'notice_of'|'issuance_of', confidence: 'high'|'medium'|'low', evidence: '별표22·별표35 겹침, 규정명 동일, 취지 키워드 3개 일치', reviewed_by, reviewed_at, state: 'auto'|'confirmed'|'rejected' }]`

| 신뢰도 | 조건 | 화면 |
|---|---|---|
| high | 규정명 동일 **그리고** 조문 겹침 ≥2 **그리고** 취지·제목 핵심어 겹침 ≥2 | 진행 현황 스텝 선에 연결 |
| medium | 규정명 동일, 조문 겹침 1 또는 핵심어 겹침 ≥3 | "연결 후보 · 원문 대조 필요" 로 상세에 별도 표시, 스텝 선에는 안 넣음 |
| low | 날짜·규정명만 | 표시 안 함(데이터에는 남김) |

- 담당자가 [연결 확인]/[연결 해제] 를 누르면 `state` 가 바뀌고 자동 재적재가 덮어쓰지 않는다.
- 기존 25건: 겹침 ≥2 인 9건만 high 유지, 나머지는 medium 으로 **강등(삭제 아님)**. 6/19↔6/29 는 low 로 내려가 화면에서 빠진다.
- 확정문이 연결되면 리포트에 "예고안 대비 확정본 차이" 절을 자동 생성(두 대비표의 조문 머리·줄 diff 비교).

### P0-4. 보도자료는 단계가 아니라 '관련 설명자료'

- 스텝 선에서 보도자료 칸을 뺀다. 상세에 **관련 자료** 목록(유형 · 발표일 · 발행기관 · 원문 · 뒷받침하는 주장)을 둔다.
- 보도자료만 있는 건은 `현재 단계 확인 필요`. 칩 이름 `보도자료만` → `단계 확인 필요(보도자료만)`.
- 연결 규칙은 P0-3 과 같은 신뢰도 체계(규정명 + 핵심어 + 날짜 범위)를 쓴다.

### P0-5. 목록 제목 = 대상 + 실질 변경, 한 줄 요약 별도

- 제목 생성 순서: ① 담당자 확정 제목(`title_manual`) → ② 대비표에서 뽑은 "조문 머리 + 변경 행위" (예: `별표35 무·저해지 해약률 산출기준 구체화(경험통계 요건·해지유보 모형)`) → ③ `config/reg_relevance.json` overrides.reason → ④ `주요 변경내용 확인 필요`.
- 추상어 검사: 제목이 `정비|합리화|명확화|개선|강화|일부개정` 으로 끝나고 구체 명사(조문·가정·기준·서식 이름)가 없으면 ②를 다시 만들거나 ④로 떨어뜨린다.
- 한 줄 요약(`summary_line`, 40~80자): 대비표 변경 항목 상위 2개 + 적용 대상. 조문에 없는 재무 영향은 쓰지 않는다.
- 메타(규정명·조문·일자·상태)는 배지로만. 보도자료 제목은 "무엇을 하겠다는 발표인지" 로 다시 쓴다(예: `계리가정 보고서 도입 발표(세칙 개정 의결)`).
- 처음 10건은 담당자가 검수한 뒤 `title_manual` 로 잠그고, 나머지는 자동 초안 + `(AI 초안)` 표시.

### P0-6. 상세 상단 "지금 어디까지 왔나요"

```
현재 사전예고 단계입니다. 최종 발령문은 아직 확인되지 않았습니다.      ← 한 문장 (stage 사전)
예고 2026.06.19 [원문]  ·  의견마감 2026.07.29 [예고문 기준]  ·  발령 미확인  ·  시행 예정 2026.10 (예고안 기준)  ·  최초 결산 반영 미확인
현재 업무상 조치: 사전검토 (AI 제안) / 담당자 확정: —
```
- 오늘 넣은 "단계 용어 안내" 를 지시서 §10 구조(쉬운 설명 → 일반 선후관계 그림 → 용어 사전)로 바꾸고 `발령`·`최초 결산 반영` 을 넣는다. 모바일은 접힘.
- 모바일 카드 순서: 상태 → 시행 여부 → 제목 → 요약.

### P0-7. 리포트 (목차는 유지)

- 제목 앞에 `[사전예고안 분석]` / `[확정 개정 분석]` / `[보도자료 정리]`.
- 결론 첫 두 문장: "본 자료는 2026.06.19 **사전예고안** 기준 분석이다. 확정 발령·시행일은 미확인이며 현행 산출기준에 적용하지 않는다."
- 첫 표에 `문서 성격 / 규정 상태 / 시행 여부 / 적용 기준일 / 최종 원문 확인 여부` 5항목.

- 조문 단위 집계와 줄 단위 집계는 이미 분리돼 있다 — "서로 다른 집계" 문구만 추가.

### 데이터 모델 (추가만, 삭제 없음)

## 4. 지시서와 다르게 보는 점 (이견)

- **개정 건 전용 테이블(`amendment_id`) 신설은 보류.** 지금 reg_items 한 건 = 문서 한 건 구조에 `relationships[]` 만 더하면 "개정 건" 은 화면에서 묶어 보여줄 수 있고(지금 `buildCases()`), 동기화·멱등 적재·화면이 모두 그대로 돈다. 별도 테이블은 2차 이후 필요가 확인되면 만든다.
- **'발령' 단독 표기는 피한다.** 행정규칙 용어로는 맞지만 팀이 쓰는 말은 "고시/개정 게시" 다. `확정 고시(발령)` · `확정 개정(발령)` 으로 병기한다.
- **최초 결산 반영일은 자동 추정하지 않는다.** 담당자 입력 필드로만 둔다.
- **제목 자동 생성은 초안이다.** 대비표가 없는 건(보도자료·일부 입법예고)은 ④ `주요 변경내용 확인 필요` 로 떨어지는 비율이 높을 것이다(예상 30~40%). 이 비율을 숨기지 않고 목록에 그대로 보인다.

## 5. 확인이 필요한 결정

1. 1차 범위(P0-1·2·3·4·6)부터 착수해도 되는가, 아니면 2·3차까지 한 번에 가는가.
2. 기존 자동 연결 중 겹침 없는 14건을 `medium`(후보)로 강등하는 것에 동의하는가 (화면에서는 "연결 후보" 로 내려가고 삭제는 안 한다).
3. 상태 문구는 §2 P0-1 표의 6개로 간다 — 바꾸고 싶은 말이 있으면 알려 달라.
4. 보도자료는 스텝 선에서 빼고 "관련 설명자료" 로만 둔다 — 동의하는가.
